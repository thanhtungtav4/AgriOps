# AgriOps Agent Mission Brief

## Product Goal

AgriOps is not just a CRUD admin. It is an agriculture operations system for farms that supply supermarkets.

The core product promise is:

> From a supermarket supply need, calculate a realistic production plan, run the farming workflow, trace packed lots by QR, and learn from actual post-season results to improve future norms after manager approval.

Every agent task must move the product toward this workflow.

## Primary User Workflow

1. Master data is configured:
   - farms, plots, beds
   - crops, varieties, growth stages
   - product standards
   - harvest, irrigation, fertilizer, labor, loss norms
2. A manager enters demand:
   - crop/variety
   - quantity and unit
   - frequency/date
   - farm
3. System calculates:
   - finished delivery quantity
   - raw harvest quantity
   - plants needed
   - planting quantity
   - area needed
   - labor/water/cost/revenue/margin
   - estimated planting date and first harvest date
4. Manager creates/approves a production plan.
5. Plan becomes planting batches with land allocation.
6. Work tasks are generated by growth stages.
7. Workers log actual farming work, photos, chemical/biological usage, and incidents.
8. Manager performs pre-harvest inspection.
9. Farm records harvest lots, processing, packing lots, QR traceability, delivery, acceptance, and returns.
10. System reports yield/loss/cost/quality and creates post-season improvement suggestions.
11. Manager approves or rejects norm updates.

## Current Important Gap

Backend/API coverage is broad, but visible site coverage is still thin.

- `/operations` needs to become the real operational UI.
- Filament admin should expose implemented backend models for management/debugging.
- The mobile field app should focus on worker task execution and logs.

## Non-Negotiable Rules For Agents

### Do Not Invent Schema

Before writing a form, resource, API payload, or table column:

1. Read the model.
2. Read the migration.
3. Read the controller/request/test if available.
4. Use only real fillable fields and real relationships.

If a useful field is missing from schema, report it as a gap. Do not invent it in UI.

### Verify Real API Contract

For frontend work:

1. Read the controller method.
2. Read feature tests for that endpoint.
3. Match required request keys exactly.
4. Match response keys actually returned.
5. If the UI displays a value that the API does not return, label it as unavailable or omit it.

Example: `POST /api/v1/planning/calculate` requires `target_date`, not `start_date` / `end_date`.

### Build Usable Workflow, Not Decorative Pages

No landing pages. No marketing-style hero UI. The first screen should help the farm operator do work.

Operational UI should be:

- dense but readable
- fast to scan
- status/action oriented
- farm/crop/date aware
- mobile responsive

### Always Write Evidence

Each agent must write an evidence file in `.sisyphus/evidence/` with:

- exact files changed
- commands run and results
- API/schema assumptions
- known remaining gaps
- verification failures, if any

### Required Verification

Use the smallest useful checks first, then broader checks:

- PHP syntax for changed PHP files
- `rtk php artisan route:list` for Filament/routes
- focused feature tests when touching API-related UI
- `rtk npm run build` when touching React
- `rtk php artisan test` before declaring backend/admin work complete

## Acceptance Criteria For Future Agent Tasks

A task is not done just because code was written. It is done only when:

1. It matches the BRD workflow.
2. It uses real schema/API contracts.
3. It passes relevant automated checks.
4. It is usable from the site/admin/mobile surface.
5. Evidence documents what was completed and what remains.
